# Day 2: HTTP, HTTPS and TLS

## Goal

Understand how browsers and servers exchange requests, how HTTP works, and how HTTPS protects communication.

## One-page summary

- **HTTP** is a stateless request/response protocol. The client starts each request.
- **Idempotent** requests can generally be repeated without changing the final resource state.
- **401** means authentication is missing or invalid; **403** means access is not allowed.
- **502** means a gateway received an invalid or unusable upstream response; **504** means the upstream took too long.
- HTTP/2 adds multiplexing but still uses TCP. HTTP/3 uses QUIC over UDP.
- **HTTPS = HTTP + TLS**. TLS provides confidentiality, integrity and authentication.
- TLS uses asymmetric cryptography for authentication/key establishment and symmetric cryptography for application data.

---

## 1. HTTP request and response

HTTP follows a request/response model: the client sends a request and the server sends a response.

### Four parts of an HTTP request

1. **Request line:** method, path and HTTP version.
2. **Headers:** extra information about the request.
3. **Blank line:** separates headers from the body.
4. **Body:** optional data sent to the server.

Example:

```http
POST /api/users HTTP/1.1
Host: example.com
Content-Type: application/json
Authorization: Bearer token123

{"name": "Sakshi"}
```

### HTTP response

A response contains a status line, headers, a blank line and an optional body.

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"id": 5, "name": "Sakshi"}
```

---

## 2. HTTP methods and idempotency

**Idempotent** means repeating the same request has the same intended effect on the resource state as sending it once.

| Method | Safe? | Idempotent? | Typical use |
|---|---|---|---|
| GET | Yes | Yes | Read data |
| HEAD | Yes | Yes | Get headers only |
| POST | No | Usually no | Create or trigger an action |
| PUT | No | Yes | Replace a resource |
| PATCH | No | Not guaranteed | Partially update a resource |
| DELETE | No | Yes | Delete a resource |
| OPTIONS | Yes | Yes | Ask about supported options; used in CORS preflight |

### PUT vs POST example

**PUT**

```http
PUT /users/5
Content-Type: application/json

{"name": "Sakshi"}
```

Sending the same request repeatedly leaves user 5 with the same intended data.

**POST**

```http
POST /orders
Content-Type: application/json

{"item": "Laptop"}
```

Sending this request repeatedly may create multiple orders.

### Why does idempotency matter?

A network failure may happen after the server has processed a request but before the client receives the response. The client may retry because it does not know whether the first request succeeded.

Retrying an idempotent operation is safer. For operations such as payments, use an **idempotency key** so repeating the same operation does not charge the customer twice.

## 3. HTTP status codes

| Range | Meaning | Examples |
|---|---|---|
| 1xx | Informational | 101 Switching Protocols |
| 2xx | Success | 200 OK, 201 Created, 204 No Content |
| 3xx | Redirection or cache validation | 301, 302, 304 Not Modified |
| 4xx | Client-side request or permission problem | 400, 401, 403, 404, 409, 429 |
| 5xx | Server or gateway problem | 500, 502, 503, 504 |

### Important status-code differences

- **401 Unauthorized:** authentication is missing or invalid — "Who are you?"
- **403 Forbidden:** the server understands who you are, but you do not have permission.
- **502 Bad Gateway:** a gateway or proxy received an invalid or unusable response from an upstream server.
- **504 Gateway Timeout:** a gateway or proxy did not receive an upstream response in time.
- **304 Not Modified:** the resource has not changed; the browser can reuse its cached copy.

---

## 4. Important HTTP headers

| Purpose | Headers | What they do |
|---|---|---|
| Caching | `Cache-Control`, `ETag`, `If-None-Match`, `Last-Modified`, `If-Modified-Since` | Control caching and check whether a cached resource is current |
| Content | `Content-Type`, `Content-Length`, `Content-Encoding`, `Accept` | Describe body format, size, compression and accepted formats |
| Host / connection | `Host`, `Connection` | Identify the target host and connection behavior |
| Authentication | `Authorization` | Send credentials such as a bearer token |
| Cookies | `Cookie`, `Set-Cookie` | Send cookies and ask the browser to store them |
| Proxy | `X-Forwarded-For`, `X-Forwarded-Proto` | Pass original client IP and protocol information |
| CORS | `Origin`, `Access-Control-Allow-Origin` | Control which browser origins may read responses |
| Security | `Strict-Transport-Security`, `Content-Security-Policy` | Set browser security policies |

### Cookie security flags

A server can set a cookie like this:

```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax
```

- **HttpOnly:** prevents JavaScript from reading the cookie through `document.cookie`. This helps reduce session-cookie theft through XSS.
- **Secure:** sends the cookie only over HTTPS.
- **SameSite:** controls when cookies are sent with cross-site requests and helps reduce CSRF risk.

### HTTP caching and 304

A browser can validate a cached resource instead of downloading it again.

1. The server sends a resource with an `ETag` or `Last-Modified` value.
2. The browser stores the resource and its validator.
3. Later, the browser sends `If-None-Match` or `If-Modified-Since`.
4. If the resource is unchanged, the server returns `304 Not Modified` without the resource body.
5. The browser uses its cached copy.

Example:

```http
HTTP/1.1 200 OK
ETag: "abc123"
```

Later request:

```http
GET /logo.png HTTP/1.1
If-None-Match: "abc123"
```

If unchanged:

```http
HTTP/1.1 304 Not Modified
```

## 5. HTTP is stateless

HTTP does not automatically remember earlier requests.

Applications maintain state using:
- Cookies
- Tokens
- Shared storage such as Redis

Stateless application servers are easier to scale because any healthy server can handle the next request.

## 6. HTTP/1.1 vs HTTP/2 vs HTTP/3

| Version | Transport | Main features |
|---|---|---|
| HTTP/1.1 | TCP | Persistent connections and Host header. Responses on one connection are ordered. |
| HTTP/2 | TCP | Multiple streams on one connection, binary framing and HPACK header compression. |
| HTTP/3 | QUIC over UDP | Independent streams, QPACK, built-in TLS 1.3 and connection migration. |

### What does each version improve?

**HTTP/1.1**
- Supports persistent connections.
- Responses on one connection are ordered.
- Browsers commonly open multiple connections to improve concurrency.

**HTTP/2**
- Uses **multiplexing**: multiple request/response streams share one TCP connection.
- Uses binary framing and HPACK header compression.
- Reduces HTTP-level head-of-line blocking.
- Still uses TCP, so packet loss can block delivery across streams on that connection.

**HTTP/3**
- Uses QUIC over UDP instead of TCP.
- Provides independent streams, so loss affecting one stream does not block delivery on other streams.
- Includes TLS 1.3 in QUIC.
- Supports connection migration, for example when a device switches from Wi-Fi to mobile data.

## 7. HTTPS and TLS

Plain HTTP traffic can be read or modified while travelling across a network. HTTPS uses TLS to protect communication.

### What TLS provides

| Security goal | How TLS helps |
|---|---|
| Confidentiality | Encrypts data so outsiders cannot easily read it |
| Integrity | Detects unauthorized changes to data |
| Authentication | Uses certificates to help verify the server's identity |

TLS sits between the application protocol and the transport connection. HTTPS commonly uses port **443**.

### Symmetric vs asymmetric cryptography

**Symmetric encryption**
- Uses the same secret key to encrypt and decrypt.
- Fast and efficient for large amounts of data.
- Examples: AES-GCM and ChaCha20-Poly1305.

**Asymmetric cryptography**
- Uses a public/private key pair.
- Used in TLS for authentication signatures and key agreement.
- Key agreement such as ECDHE helps both sides establish a shared secret.

**Why does TLS use both?**

Asymmetric techniques help authenticate the server and establish shared keys. Symmetric encryption is much faster for protecting the application data that follows.

> Important: modern TLS 1.3 does not use RSA key transport. It commonly uses ephemeral Diffie-Hellman key agreement such as ECDHE.

## 8. TLS certificates

A TLS certificate binds a domain name to a public key.

For example, a certificate for `example.com` tells the browser that the public key in the certificate is associated with that domain.

A **Certificate Authority (CA)** digitally signs the certificate to help browsers trust that binding.

### Certificate chain

```text
Website certificate
        |
Intermediate CA
        |
Trusted root CA
```

The root CA is generally included in the browser or operating system's trust store.

### What does the browser check?

1. Does the certificate chain lead to a trusted root?
2. Does the domain match the certificate's name (SAN)?
3. Is the certificate within its validity period?
4. Is the certificate's signature valid?
5. Is there relevant revocation information?

If important checks fail, the browser may show a certificate warning.

## 9. TLS 1.3 handshake

A simplified TLS 1.3 handshake:

```text
Client                         Server
  | ------ ClientHello --------> |
  | <----- ServerHello --------- |
  | <----- Certificate + Finished
  |                              |
  | ------ Finished -----------> |
  |                              |
  |   Encrypted application data |
```

- **ClientHello:** offers TLS settings, cipher suites, key share, SNI and other extensions.
- **ServerHello:** selects settings and sends its key share.
- **Certificate:** helps the client verify the server's identity.
- **Finished messages:** confirm that the handshake has been completed correctly.
- Both sides derive shared symmetric session keys and use them for application data.

### TLS versions and RTT

- A full TLS 1.2 handshake commonly takes **2 RTTs**.
- A full TLS 1.3 handshake takes **1 RTT** after the transport connection is established.
- TLS 1.3 removes older, weaker cryptographic options and uses forward-secret key exchange.

### Session resumption and 0-RTT

- **Session resumption:** allows a returning client and server to resume a previous session, reducing handshake work.
- **0-RTT early data:** allows certain data to be sent before the resumed handshake is fully complete.
- 0-RTT data can be replayed, so it should only be used for operations where replay is safe.

## 10. Important TLS terms

- **SNI (Server Name Indication):** the client sends the hostname in the TLS handshake so one IP address can host multiple HTTPS websites and select the correct certificate.
- **Forward secrecy:** ephemeral key exchange helps protect past sessions even if the server's long-term private key is compromised later.
- **HSTS:** tells browsers to use HTTPS for a domain and helps prevent downgrade to HTTP.
- **TLS termination:** a load balancer or reverse proxy decrypts incoming HTTPS traffic. It may forward plain HTTP internally or establish a new TLS connection to the backend.
- **mTLS (Mutual TLS):** both the server and client authenticate using certificates. It is often used between services.
- **ALPN:** negotiates the application protocol, such as HTTP/2, during the TLS handshake.

### What HTTPS does not hide completely

HTTPS protects the contents of communication, but it does not automatically hide all connection metadata. The destination IP is generally visible to the network. DNS queries and traditional SNI can also reveal the domain name, unless privacy technologies such as encrypted DNS and Encrypted ClientHello are used.

HTTPS also does not protect an application from vulnerabilities such as SQL injection, XSS or a malicious server.

## 11. Cold HTTPS request — RTT cost

**RTT** means round-trip time: the time for a message to travel to the other side and for a response to return.

Assume:
- DNS is not cached.
- No TCP connection is already open.
- A full TLS 1.3 handshake is used.
- No session resumption or 0-RTT is used.
- There are no extra redirects or proxies adding setup time.

| Step | Approximate RTT |
|---|---:|
| DNS lookup, if not cached | 1 or more |
| TCP handshake | 1 |
| Full TLS 1.3 handshake | 1 |
| HTTP request and response | 1 |
| **Total with one DNS RTT** | **About 4 RTTs** |

DNS can take more than one RTT on a cold lookup. A cached DNS result removes that lookup cost.

### How to reduce request time

- **Keep-alive / connection pooling:** reuse an existing connection instead of repeating TCP and TLS setup.
- **DNS caching / prefetch:** avoid waiting for repeated DNS lookups.
- **CDN:** serve content from a location closer to the user.
- **TLS 1.3 / session resumption:** reduce handshake time.
- **HTTP/3:** uses QUIC and can reduce connection setup overhead in suitable situations.

## Common interview traps

- Saying HTTP/2 completely removes head-of-line blocking. It removes HTTP-level blocking, but TCP-level blocking remains.
- Saying HTTPS encrypts application data using the public key. TLS uses symmetric session keys for application data.
- Mixing up 401 and 403, or 502 and 504.
- Forgetting why POST is generally not safe to retry.
- Forgetting that DNS and traditional SNI can reveal domain information.
- Saying a certificate proves that a website is safe. It helps authenticate the domain-to-key relationship; it does not guarantee the website is harmless.
