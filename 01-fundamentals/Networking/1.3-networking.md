# Day 3: URL to Render + System Design Hooks

## Goal

Understand what happens after you enter a URL in the browser — from local browser checks and DNS to the server response and final page rendering.

## One-page summary

The complete flow:

```text
URL
 ↓
Browser checks and cache
 ↓
DNS → IP address
 ↓
TCP connection
 ↓
TLS handshake
 ↓
HTTP request
 ↓
CDN → Load balancer → Reverse proxy → App
 ↓
Redis cache → Database (if needed)
 ↓
HTTP response
 ↓
DOM + CSSOM → Render tree → Layout → Paint → Composite
```

Key ideas:

- A request may be answered by the browser cache, service worker or CDN without reaching the origin server.
- Every network round trip adds latency. Reuse connections and serve content closer to users.
- CSS can block rendering; normal synchronous JavaScript can block HTML parsing.
- Stateless app servers are easier to scale horizontally.
- Retry only safe/idempotent operations, with timeouts, exponential backoff and jitter.

## 1. What happens when you enter a URL?

Example:

```text
https://shop.example.com:443/products?id=5#reviews
```

| Part | Meaning |
|---|---|
| Scheme | `https` |
| Host | `shop.example.com` |
| Port | `443` (default HTTPS port) |
| Path | `/products` |
| Query | `id=5` |
| Fragment | `#reviews` — handled by the browser, not sent to the server |

### Browser's local checks

Before making a network request, the browser may:

1. Decide whether the input is a URL or a search query.
2. Check **HSTS**. If the domain requires HTTPS, upgrade HTTP to HTTPS locally.
3. Check a registered **service worker**, which may intercept or answer the request.
4. Check the HTTP cache:
   - Fresh cached response: use it without a network request.
   - Stale response with a validator: ask the server if it changed.
   - No cached response: make a full request.
5. Reuse an existing connection to the host if one is available.

**Important:** A browser cache hit can avoid the entire network trip.

## 2. DNS and connecting to the server

### DNS

DNS translates a domain name into an IP address.

A simplified lookup path:

```text
Browser cache
    ↓
OS cache / hosts file
    ↓
Recursive resolver
    ↓
Root DNS server
    ↓
TLD server (.com)
    ↓
Authoritative DNS server
    ↓
IP address (A or AAAA record)
```

- **Happy Eyeballs:** browsers may try IPv6 and IPv4 connections close together and use the one that connects successfully first.
- **CDN DNS:** DNS may direct the user to a nearby CDN edge.
- Cached DNS results can make lookup effectively take no network round trip.

### TCP handshake

For HTTP/1.1 and HTTP/2 over TCP, a new connection uses:

```text
Client                 Server
  | ------ SYN -------> |
  | <--- SYN-ACK ------ |
  | ------ ACK -------> |
```

This takes approximately **1 RTT**.

- The handshake establishes connection state and synchronizes sequence numbers.
- TCP Fast Open can sometimes send data earlier on repeat connections.
- A new TCP connection starts with congestion control's slow-start behavior.

HTTP/3 uses QUIC over UDP instead of establishing a separate TCP connection.

### TLS handshake

For HTTPS, TLS establishes encryption and authenticates the server.

The client sends a `ClientHello` with supported settings, key share, SNI and ALPN. The server responds with its selected settings, key share and certificate information. The client verifies the certificate, both sides derive shared session keys, and the handshake is completed.

- **SNI:** tells the server which hostname the client wants.
- **ALPN:** negotiates the application protocol, such as HTTP/2.
- TLS 1.3 full handshake: about 1 RTT.
- TLS 1.2 full handshake: commonly about 2 RTTs.
- Session resumption can reduce setup work.

## 3. The HTTP request

After the connection is ready, the browser sends an HTTP request.

```http
GET /products?id=5 HTTP/1.1
Host: shop.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: sid=abc
```

Cookies for the domain are attached automatically when cookie rules allow it.

HTTP/2 and HTTP/3 carry the request information using binary frames rather than the text format of HTTP/1.1.

## 4. What happens on the server side?

This is the part that is often missed when explaining a page load.

```text
Client
  ↓
CDN
  ↓ (cache miss)
Load balancer
  ↓
Reverse proxy / API gateway
  ↓
Application server
  ↓
Redis cache
  ↓ (cache miss)
Database
```

The response travels back through the server-side layers.

### 4.1 CDN

A **Content Delivery Network** stores content at edge servers closer to users.

- **Pull CDN:** fetches content from the origin on the first cache miss, then stores it.
- **Push CDN:** content is uploaded to the CDN ahead of time.
- Useful for static files, images, videos and carefully selected cacheable API responses.
- Usually unsuitable for personalized responses or write requests.

Important CDN concepts:

- **Cache key:** identifies which request a cached response belongs to. It is usually based on the URL and selected headers.
- **TTL:** controls how long a response can remain cached.
- **`Cache-Control` / `s-maxage`:** control caching, including shared caches.
- **`Vary`:** tells caches which request headers affect the response.
- **Invalidation:** remove old cached content. Versioned filenames such as `app.3f9a1.js` make asset updates easier.
- CDNs can also provide TLS termination, compression, DDoS absorption and origin shielding.

A wrong cache key can cause one user's personalized response to be served to another user.

### 4.2 Load balancer

A load balancer distributes incoming traffic across multiple application servers and avoids sending traffic to unhealthy servers.

**L4 vs L7**

| Type | Looks at | Example capability |
|---|---|---|
| L4 | IP address and port; TCP/UDP | Forward traffic to a server |
| L7 | HTTP details such as path, headers and cookies | Route `/api` and `/static` to different server pools |

**Common balancing algorithms**

| Algorithm | Simple explanation |
|---|---|
| Round robin | Send requests to servers in turn |
| Weighted round robin | Give stronger servers more requests |
| Least connections | Choose the server with fewer active connections |
| IP hash / consistent hash | Map the same client or key to the same server |
| Power of two choices | Pick two servers and choose the less loaded one |

**Health checks**
- Active: the load balancer periodically calls a health endpoint.
- Passive: it observes failures while handling real traffic.
- Unhealthy servers are removed from rotation.

**Sticky sessions** keep a user on the same server. They can be useful, but they make scaling and failover harder. Prefer stateless servers with shared session storage when possible.

**Connection draining:** during deployment, stop sending new requests to a server but allow existing requests to finish.

The load balancer itself must not become a single point of failure.

### 4.3 Reverse proxy / API gateway

Examples include Nginx, HAProxy, Envoy and API gateway products.

Common responsibilities:

- TLS termination
- Request routing
- Authentication or JWT validation
- Rate limiting
- Request-size limits
- Compression
- Logging and request IDs
- Retries and circuit breaking
- Buffering requests before they reach the app

It may add headers such as:

- `X-Forwarded-For`: original client IP information
- `X-Forwarded-Proto`: original request protocol
- `X-Request-Id`: request tracing identifier

Rate limiting can use algorithms such as token bucket or sliding window. A limited client commonly receives **429 Too Many Requests**, sometimes with `Retry-After`.

### 4.4 Application server

For a Node.js / Express application:

1. Parse the incoming request.
2. Run middleware such as authentication, validation and logging.
3. Execute the route handler and business logic.
4. Read or update cache/database as needed.
5. Build and send the response.

Node.js uses a single-threaded event loop for JavaScript execution. Avoid long CPU-heavy work on the event loop. Scale using multiple processes or containers when needed.

Keep application servers **stateless**:
- Do not keep important user sessions only in local process memory.
- Use tokens or shared storage such as Redis.
- Any healthy instance should be able to handle the next request.

### 4.5 Redis cache

Redis provides fast in-memory lookups so the application can avoid repeatedly querying the database.

**Cache patterns**

| Pattern | How it works | Trade-off |
|---|---|---|
| Cache-aside | App checks cache; on miss, reads DB and fills cache | Common and simple; stale data is possible |
| Read-through | Cache layer loads data from DB on a miss | Simpler application logic |
| Write-through | Write to cache and DB together | Better consistency, slower writes |
| Write-back | Write to cache, persist to DB later | Fast, but data can be lost before persistence |
| Write-around | Write to DB; cache fills on later reads | Avoids caching data that may never be read |

**TTL** limits how long data stays cached. **Eviction** such as LRU or LFU removes entries when memory is full.

**Common cache problems**

- **Cache stampede:** many requests hit the database when a popular key expires. Use locking/single-flight, jittered TTLs or early refresh.
- **Cache penetration:** requests for nonexistent keys repeatedly hit the database. Cache negative results or use a Bloom filter.
- **Cache invalidation:** cached data becomes outdated. Use TTLs and invalidate/update cache entries when data changes.

### 4.6 Database

The database is usually the source of truth.

Ways to improve database performance and scale:

- **Indexes:** speed up suitable queries.
- **Query tuning:** avoid inefficient queries and N+1 patterns.
- **Read replicas:** distribute reads; replication lag can mean slightly stale data.
- **Connection pooling:** reuse a limited set of database connections.
- **Sharding:** split data across multiple database nodes for very large workloads.

Be careful with pool size. If many app instances each open a large pool, the database can run out of connections.

## 5. The HTTP response

Example:

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Encoding: br
Cache-Control: public, max-age=60
ETag: "abc123"
```

The response may be compressed using Brotli or gzip. It travels back through the server-side layers.

- A redirect such as 301 or 302 can require another request.
- A 304 response tells the browser to reuse its cached copy.
- With streaming, the server can start sending HTML before the entire page is ready.

## 6. How the browser renders the page

The browser turns downloaded HTML and CSS into pixels on the screen.

```text
HTML bytes → Characters → Tokens → DOM
CSS bytes  → CSSOM

DOM + CSSOM
     ↓
Render tree
     ↓
Layout
     ↓
Paint
     ↓
Composite
```

### Rendering steps

1. **HTML parsing:** browser converts HTML into the DOM (Document Object Model).
2. **Preload scanner:** looks ahead for resources such as CSS, scripts and images and may start downloading them early.
3. **CSS parsing:** browser builds the CSSOM (CSS Object Model).
4. **JavaScript execution:** scripts can affect parsing and rendering.
5. **Render tree:** combines DOM and CSSOM for visible content.
6. **Layout:** calculates the size and position of elements.
7. **Paint:** draws text, colors, borders, shadows and other visual details.
8. **Composite:** combines layers into the final screen image, often using the GPU.

### What blocks what?

**CSS**
- CSS is render-blocking because the browser needs styles before painting the page correctly.
- CSS can also delay scripts that may need to inspect styles.

**JavaScript**

| Script type | Behavior | Typical use |
|---|---|---|
| Normal `<script>` | Downloads and executes while HTML parsing is paused | Small scripts that must run immediately |
| `async` | Downloads in parallel; executes as soon as ready and pauses parsing during execution | Independent scripts such as analytics |
| `defer` | Downloads in parallel; executes after HTML parsing, in document order | Application scripts |
| `type="module"` | Deferred by default | JavaScript modules |

### Layout vs paint vs composite

| Operation | What changes? | Relative cost |
|---|---|---|
| Layout / reflow | Element size or position | Usually expensive |
| Paint | Visual appearance such as color or shadow | Can be expensive |
| Composite | Combining existing layers | Often cheapest |

For smoother animations, prefer `transform` and `opacity` when possible because they can often be handled at the compositing stage.

**Layout thrashing** happens when code repeatedly reads layout values and writes styles in a loop, forcing repeated layout calculations. Batch reads together and writes together.

### Important browser metrics

| Metric | Meaning |
|---|---|
| TTFB | Time to First Byte |
| FCP | First Contentful Paint |
| LCP | Largest Contentful Paint; when the main visible content appears |
| CLS | Cumulative Layout Shift; unexpected movement of page content |
| INP | Interaction to Next Paint; responsiveness to user interactions |

## 7. Sub-resources and connection reuse

After receiving HTML, the browser may download CSS, JavaScript, images and fonts. JavaScript may also make API requests.

- Requests to the same origin can reuse a connection.
- Requests to other origins may need DNS and connection setup.
- Resource hints can start work earlier.

| Hint | Purpose |
|---|---|
| `dns-prefetch` | Resolve a domain name early |
| `preconnect` | Start DNS, TCP and TLS setup early |
| `preload` | Fetch a critical resource early |
| `prefetch` | Fetch a resource that may be needed on a future page |

Other optimizations:
- Lazy-load images that are below the fold.
- Use correctly sized images and modern formats such as WebP or AVIF.
- Use `font-display: swap` to avoid invisible text while a font loads.
- Keep connections alive for reuse.

## 8. CSR vs SSR vs SSG

| Approach | How it works | Advantages | Trade-off |
|---|---|---|---|
| CSR | Browser downloads JavaScript, calls APIs and renders | Less server rendering work | Slower first content in some cases; SEO can be harder |
| SSR | Server creates HTML for each request | Good initial HTML and SEO | More server work |
| SSG | HTML is created during build and served as static files | Very fast; CDN-friendly | Content can become stale until rebuilt |
| ISR / hybrid | Static pages are regenerated periodically or on demand | Balances speed and freshness | More complexity |

Examples:
- Blog: SSG is often a good fit.
- Frequently changing dashboard: CSR or SSR may fit, depending on the requirements.
- Product store: SSR or SSG/ISR can work depending on how frequently product data changes.

## 9. Latency: where does the time go?

**RTT** means round-trip time: the time for a message to reach the other side and for a response to return.

A simplified cold HTTPS request:

| Step | Approximate RTT |
|---|---:|
| DNS lookup | 1 or more |
| TCP handshake | 1 |
| TLS 1.3 handshake | 1 |
| HTTP request and response | 1 |
| **Total** | **About 4 RTTs** |

If the RTT to the origin is 100 ms, the network setup and request/response can take about 400 ms under these assumptions, before considering extra server processing or downloads.

### Common latency problems and fixes

| Problem | Possible fixes |
|---|---|
| DNS lookup | DNS caching, `dns-prefetch`, suitable TTL |
| TCP/TLS setup | Keep-alive, connection pooling, TLS 1.3, session resumption, `preconnect` |
| Server is far away | CDN, multi-region deployment, edge computing |
| Slow application or DB | Redis, indexes, async jobs, avoid N+1 queries |
| Large payloads | Brotli/gzip, minification, code splitting, image optimization |
| Blocking resources | `async`, `defer`, critical CSS, `preload` |
| Redirect chains | Reduce unnecessary redirects |

### How to debug a slow page

Measure before changing things.

1. Open browser DevTools → Network.
2. Check **TTFB** to investigate network/backend delay.
3. Check download time and response size.
4. Open Performance tools or Lighthouse to investigate rendering.
5. Fix the largest bottleneck first.

## 10. System design concepts

### Forward proxy vs reverse proxy

| Forward proxy | Reverse proxy |
|---|---|
| Sits in front of clients | Sits in front of servers |
| Handles outbound client traffic | Handles incoming server traffic |
| Example: corporate proxy or VPN | Example: Nginx |
| Can filter or cache client requests | Can route, cache, balance and secure server traffic |

### Stateless servers

A stateless server does not depend on local memory to remember a user's previous request.

- Store session state in a shared store such as Redis, or use suitable tokens.
- Any healthy app instance can handle any request.
- This makes horizontal scaling and failover easier.

### Connection pooling

Opening a database or upstream connection takes time and resources. A connection pool keeps a limited number of connections open and reuses them.

- Pool too small: requests wait for a free connection.
- Pool too large: the database or upstream service can be overloaded.

### Timeouts

Set:
- **Connect timeout:** maximum time to establish a connection.
- **Read timeout:** maximum time to wait for data.
- **Overall deadline:** maximum time allowed for the complete operation.

Without timeouts, slow dependencies can hold connections and resources for too long, causing failures to spread.

Timeouts should be coordinated across the call chain. Inner services should generally have shorter deadlines than the outer caller, leaving time for the outer layer to handle the failure.

### Keep-alive timeout mismatch

A common production problem:

1. The app server closes an idle connection.
2. The load balancer still believes the connection is open.
3. The load balancer sends a request through that stale connection.
4. The request fails, possibly producing a random 502.

The source notes' rule:

**App/server keep-alive timeout should be greater than the load balancer idle timeout.**

The notes also highlight a Node.js example: the default `server.keepAliveTimeout` can be lower than a cloud load balancer's idle timeout. Check the actual values in your deployment environment.

### Retries

Retry only:
- Idempotent operations such as GET, PUT and DELETE.
- Non-idempotent operations when protected by an idempotency key.

**Exponential backoff:** increase the wait between attempts, for example 100 ms → 200 ms → 400 ms.

**Jitter:** add randomness to retry delays so many clients do not retry at exactly the same time.

Also:
- Set a maximum number of attempts.
- Set a total time budget.
- Avoid retries at every layer because retry counts multiply. For example, 3 layers with 3 attempts each can create up to 27 downstream attempts.

### Resilience patterns

| Pattern | Meaning |
|---|---|
| Circuit breaker | Temporarily stop calling a failing dependency; later test whether it recovered |
| Bulkhead | Isolate resources so one failing dependency cannot consume everything |
| Rate limiting | Limit request volume to protect the service |
| Load shedding | Drop lower-priority work during overload |
| Graceful degradation | Return partial or cached data when possible |
| Health checks and draining | Remove unhealthy servers and let active requests finish during deployment |

### Idempotency keys for payments

A client sends a unique key with a payment request:

```http
POST /payments
Idempotency-Key: 7f4c-example-uuid
```

The server stores the key and the result. If the client retries with the same key, the server returns the saved result instead of charging again.

## 11. Real-time communication choices

| Method | How it works | Best fit |
|---|---|---|
| Polling | Client asks the server repeatedly | Simple, low-frequency updates |
| Long polling | Server holds a request until data or timeout | Older chat/notification designs |
| SSE | Server sends a one-way event stream over HTTP | Feeds, notifications, progress |
| WebSocket | Persistent two-way connection | Chat, collaboration, games, live trading |

### WebSocket scaling

A WebSocket connection stays attached to one server. If users are connected to different servers, use a shared messaging system such as Redis Pub/Sub or Kafka to distribute messages between instances.

You also need connection handling such as heartbeats, reconnect logic and appropriate load-balancer support.

## 12. Caching layers

From the browser towards the database:

| Layer | Scope | Common control |
|---|---|---|
| Browser memory/disk cache | One user | `Cache-Control`, `ETag` |
| Service worker | One user | Application JavaScript |
| CDN | Many users in a region | `s-maxage`, `Vary`, purge |
| Reverse proxy cache | Users of that proxy | Proxy configuration |
| Application cache (Redis) | All app servers | Application code and TTL |
| Database buffer/cache | Database internals | Database configuration |

**Rule:** the earlier a request is answered, the more work is avoided. But every extra cache layer adds invalidation and stale-data risks.

---

## 13. Scaling vocabulary

- **Vertical scaling:** use a larger machine. Simple, but has limits and can remain a single point of failure.
- **Horizontal scaling:** add more machines. Usually requires a load balancer and stateless application design.
- **Single point of failure (SPOF):** one component whose failure can bring down the whole service. Redundancy helps remove SPOFs.
- **Availability:** design each part of the system to handle failures, including CDN, load balancer, proxy, app, cache and database.

---

## 14. Failure modes along the request path

| Component | Possible failure | Example mitigation |
|---|---|---|
| DNS | Resolver failure or stale record | Multiple resolvers, suitable TTL |
| TCP | Packet loss, SYN flood, port exhaustion | Connection reuse, SYN cookies |
| TLS | Expired or incorrect certificate | Automatic renewal and expiry monitoring |
| CDN | Wrong cache key or stale content | Correct cache rules, versioned URLs, purge |
| Load balancer | No healthy backends or timeout mismatch | Health checks, coordinated timeouts |
| App | Crash, blocked event loop, slow dependency | Timeouts, circuit breaker, restart policy |
| Cache | Cache outage or stampede | Controlled DB fallback, locking, TTL jitter |
| Database | Slow query or exhausted connections | Indexes, query tuning, connection pooling |
| Browser | Blocking CSS/JS or huge bundle | Defer scripts, code splitting, compression |

## Common interview traps

- Explaining DNS only as "domain to IP" without mentioning caching, TTL and the hierarchy.
- Mixing up TCP and TLS handshakes.
- Explaining only the browser side and skipping CDN, load balancer, proxy, app, cache and database.
- Saying "add a cache" without explaining the cache pattern, TTL and invalidation.
- Saying every request should be retried. Retries need idempotency, timeouts, backoff and jitter.
- Saying HTTP/2 removes all head-of-line blocking. TCP-level blocking remains.
- Forgetting the rendering stages: DOM, CSSOM, render tree, layout, paint and composite.
